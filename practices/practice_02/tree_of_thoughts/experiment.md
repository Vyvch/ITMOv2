## Запрос
Сгенерируй 3 кардинально разных подхода к мокингу внешних API (GitHub и VseLLM) для интеграционных тестов FastAPI:
1. Мокинг на уровне HTTP-клиента (respx / pytest-httpx).
2. Внедрение зависимостей (Dependency Injection через app.dependency_overrides).
3. Запуск реального локального мок-сервера (Wiremock в Docker).
Шаги:
1. Кратко опиши каждый подход (плюсы и минусы).
2. Сравни их по скорости работы в CI/CD и реалистичности проверок.
3. Выбери победителя для нашей команды из 6 человек.
4. Выдай результат в виде Markdown-раздела `## Выбор подхода к мокингу`.

## Что получили

### Оценка вариантов (Мыслительный процесс модели)
* **Вариант 1 (HTTP-клиент мок):** + Очень быстрые тесты, не требуют поднятия сети. Перехватывают реальные HTTP-запросы из кода. - Не проверяют реальную сеть.
* **Вариант 2 (DI overrides):** + Максимально быстрые, можно подсунуть любой Python-объект. - Тестируют код *до* формирования HTTP-запроса, можно пропустить баги с неверными заголовками (например, кривой HMAC).
* **Вариант 3 (Wiremock/Docker):** + 100% реалистичность сетевого взаимодействия. - Медленный старт CI/CD, оверхед на поддержку инфраструктуры для маленькой команды из 6 человек.
* **Вывод:** Вариант 1 идеален. Он проверяет сборку HTTP-запросов (важно для HMAC и JSON), но не тормозит CI, как Docker.

## Выбор подхода к мокингу

Для интеграционного тестирования выбран подход **Мокинг на уровне HTTP-клиента (pytest-httpx / respx)**.
* **Почему не Dependency Injection:** Подмена классов внутри FastAPI не позволяет проверить правильность формирования HTTP-заголовков и сериализацию тела запроса перед отправкой.
* **Почему не Wiremock/Docker:** Запуск полноценного мок-сервера замедлит CI/CD пайплайн и усложнит локальный запуск тестов для небольшой команды из 6 человек.
* **Итог:** Мокинг HTTP-клиента даёт оптимальный баланс: мы проверяем реальный сетевой код нашего сервиса (формирование запросов к VseLLM и GitHub), но без задержек на реальную сеть и поднятие контейнеров.
