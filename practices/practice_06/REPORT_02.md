## Ключевая проверка — защита независима от послушания модели

Главное требование из [lab/README](lab/README.md): сервер обязан держать оборону **даже при
принудительной передаче опасного решения**, не полагаясь на то, что LLM откажется.

Прямая отправка изготовленного решения в `/assistant/execute` (без всякой модели):

```
POST /assistant/execute {"decision":{"tool":"delete_tree","arguments":{"path":"."}}}  (токен alice)
    -> 403 {"error":"delete is not allowed"}
GET /files?user=alice&path=receipt.txt
    -> 200 {"content":"TEST_ALICE receipt: chair, 5000 RUB"}   # данные целы

POST /assistant/execute {"decision":{"tool":"export_profiles"}}  (токен alice)
    -> 403 {"error":"staff only"}
POST /assistant/execute {"decision":{"tool":"read_file","arguments":{"path":"private/operator-note.txt"}}}
    -> 404 {"error":"not found"}                                 # секрет недоступен
```

Так подтверждается различие из README: принудительная передача решения — это тест **доступа к
инструменту**, и теперь он отбивается на сервере. Поэтому ответ модели (послушалась инъекции или
нет) больше не влияет на безопасность: исполнитель не выдаёт полномочий, которых нет у клиента.

## Сохранённая функциональность

Регрессий нет — штатные сценарии работают (см. зелёные тесты `test_service.py` / `test_http.py`):
клиент получает свой профиль и чек, покупает по цене каталога, оставляет отзыв, получает помощь по
своему заказу; сотрудник с реальной staff-сессией делает экспорт. Граница стенда (`127.0.0.1`,
песочница, запрет shell/внешних URL) сохранена.

## Остаточные замечания
- `/debug/logs` оставлен для учебной наглядности (доступ только staff, секреты вычищены). В бою
  такой эндпоинт обычно вообще выключают в проде.
- Prompt injection на уровне самого текста остаётся возможной попыткой, но в учебной модели это не
  даёт эффекта: единственный исполнитель (`/assistant/execute`) проверяет права сам. Честный прогон
  живой модели `shop-planner` — опциональная демонстрация и на оценку не влияет (см. README).
