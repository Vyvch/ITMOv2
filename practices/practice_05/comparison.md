# OpenSpec и Spec Kit: сравнение на одном проекте

Оба фреймворка применялись к одному проекту — `practices/practice_05/domains_project`
(сайт освобождающихся доменов .ru/.su/.рф на FastAPI).

| | OpenSpec | Spec Kit |
|---|---|---|
| Фича | `regex-search` — поиск по регулярному выражению | `wayback` — история домена в веб-архиве, две команды: интерфейс (`001-wayback-ui`) и сервер (`002-wayback-api`) |
| Где лежит | `openspec/changes/archive/2026-10-28-regex-search/`, `openspec/specs/domain-search/` | `.specify/memory/constitution.md`, `specs/001-wayback-ui/`, `specs/002-wayback-api/`, `specs/wayback-contract.md` |
| Коммиты | `9a1ee38` | `707f677` (спеки до согласования) → `5279c87` (после) → `0d4e4c3` → `d038980` → `97e2d2d` → `ab0db60` |

Задачи разного размера, поэтому сравнение по объёму не вполне честное: regex — одна небольшая фича,
wayback — две связанные фичи с внешним сервисом. Ниже — то, что заметно независимо от размера.

## Процесс

| | OpenSpec | Spec Kit |
|---|---|---|
| Шаги | `explore` → `propose` → `apply` → `sync`/`archive` (+ `update` по необходимости) | `constitution` → `specify` → `clarify` → `plan` → `tasks` → `analyze` → `implement` |
| Артефакты на фичу | 4: `proposal`, `spec` (delta), `design`, `tasks` | 8+: `spec`, `checklists/requirements`, `plan`, `research`, `data-model`, `contracts/`, `quickstart`, `tasks` |
| Принципы проекта | нет отдельного документа; правила — в `openspec/config.yaml` (`context`, `rules`) | конституция (`constitution.md`) — принципы с номерами, план проверяется на соответствие до и после проектирования |
| Модель спецификаций | основная спека + изменения поверх неё (delta, `ADDED`/`MODIFIED`); после archive спека — «истина» для следующих фич | каждая фича — своя папка `specs/NNN-…`; общей «главной» спеки нет |
| Проверка до кода | ревью в отдельном чате (вручную) | `/speckit-analyze` — встроенная сверка spec ↔ plan ↔ tasks ↔ конституция |
| Активная фича | изменение называется по имени в каждой команде (`/opsx:apply regex-search`) | одна «текущая фича» на проект в `.specify/feature.json` |

## Что понравилось

**OpenSpec**
- Мало шагов, их легко держать в голове. Сформулировал, агент написал документы, прочитал, разрешил код.
- Дешевле по токенам и быстрее: меньше документов, агент меньше читает и пишет.
- Delta-спецификации и `archive` дают честную историю: основная спека `domain-search` описывает то,
  что реально работает, а завершённое изменение уходит в архив.
- Удобно для небольшой фичи в существующем проекте.

**Spec Kit**
- Конституция задаёт правила один раз, и они реально применялись: TDD (тест до кода в каждой задаче),
  «внешние сервисы только через сервер», безопасный вывод в DOM. На этапе конституции она сразу нашла
  существующие нарушения (`innerHTML` с внешними данными).
- `/speckit-analyze` нашёл ошибки, которые иначе всплыли бы только в коде: таймаут `httpx` 5 с вместо 10,
  отсутствие `AbortController` в тестовой песочнице, задачи без теста до кода, порядок задач.
- `research.md` с отвергнутыми альтернативами — видно, почему выбрано именно так.
- Для двух команд удобно: «Ожидания от сервера» в спеке интерфейса + общий `wayback-contract.md`
  с версиями (1.0 → 1.2) и историей согласований.

## Что мешало

**OpenSpec**
- Нет встроенной проверки согласованности — ревью делали вручную в отдельном чате.
- Нет места для общих принципов проекта, кроме `config.yaml`.

**Spec Kit**
- Много шагов и документов: дороже по токенам и дольше, для небольшой фичи — избыточно.
- Одна «текущая фича» на проект: две команды в одной папке постоянно перетягивали `.specify/feature.json`,
  приходилось работать строго по очереди и каждый раз указывать папку явно. В реальности команды разнесли бы
  по git worktree.
- Нет понятия «основной спецификации» и архива: после реализации спеки остаются в `specs/NNN-…` как есть.
- Агенты склонны раздувать артефакты (35 и 30 задач, спеки по 300–400 строк) — их нужно читать, иначе
  согласование превращается в формальность.

## Общее для обоих

- Решения принимает человек: оба фреймворка останавливаются перед кодом и ждут подтверждения.
- Правило «сначала спецификация, потом код» держится в обоих: когда реальные данные разошлись
  с допущениями (холодный запрос к архиву 17,5 с при таймауте 10 с; блокировка архива при интервале 1 с),
  сначала правилась спека и контракт, потом код.
- Качество результата больше зависит от того, насколько внимательно человек читает документы и задаёт
  границы, чем от выбора фреймворка.

## Вывод

| Ситуация | Что выбрать |
|---|---|
| Небольшая фича в существующем проекте, один исполнитель | OpenSpec |
| Фича с внешними сервисами, несколькими частями или командами, нужен контракт и строгие правила | Spec Kit |
| Долгоживущий проект, где важна актуальная «главная» спецификация | OpenSpec (delta + archive) |
| Нужна автоматическая проверка согласованности до кода | Spec Kit (`/speckit-analyze`) |
