# Research: История домена в веб-архиве (сервер)

Все пункты Technical Context определены; `NEEDS CLARIFICATION` не осталось. Ниже — решения,
принятые при проектировании, с обоснованием и отвергнутыми вариантами.

## R1. Запрос к Wayback CDX

- **Decision**: один GET `https://web.archive.org/cdx/search/cdx` с параметрами
  `url=<punycode-домен>`, `fl=timestamp,original`, `limit=100000`, без `output=json` (ответ —
  строки `<14 цифр> <исходный адрес>` через пробел, по возрастанию времени). Если строк ровно
  100 000 — второй запрос через ту же очередь с `limit=-1&fastLatest=true` за последним снимком.
- **Rationale**: `url=<домен>` без `matchType` — это главная страница; CDX канонизирует адрес
  (SURT `ru,example)/`), поэтому `http`/`https` и `www.` попадают в один набор — тот же, что на
  `web.archive.org/web/*/<домен>` (FR-005). Один запрос даёт и счёт, и первый, и последний снимок
  (FR-006) — минимум нагрузки на лимиты. Текстовый формат проще и легче JSON на больших списках.
- **Alternatives considered**: три запроса (`showNumPages`/счёт, `limit=1`, `limit=-1`) — втрое
  больше обращений к лимитированному архиву; `matchType=domain` — считает все страницы и поддомены,
  расходится со ссылкой интерфейса; `collapse=timestamp:8` (по дням) — меняет смысл «числа снимков».
- **Проверить при реализации — первая задача `tasks.md`**: один раз вручную снять реальные ответы
  CDX тем же запросом, что будет в коде, и сохранить в `tests/fixtures/wayback/` как образцы:
  - `cdx_regular.txt` — обычный домен `.ru` с десятками–сотнями снимков (если ответ больше ~200 КБ,
    взять домен поменьше);
  - `cdx_empty.txt` — домен без снимков (ожидается пустое тело при 200);
  - `capture.md` — дата съёмки, точные адреса запросов, HTTP-статусы и значимые заголовки, имена
    доменов.

  Если по пути удастся получить ответ на исключённый из архива сайт — сохранить как
  `cdx_blocked.txt`; иначе признак из R2 остаётся допущением и проверяется синтетической строкой.
  Тесты разбора используют только эти файлы, сеть в тестах не используется (принцип II). Образцы
  подтверждают или исправляют допущения R1–R2 до написания разборщика.

## R2. Разбор ответа и крайние случаи архива

- **Decision**:
  - пустое тело при 200 → «нет снимков»;
  - строка валидна, если первое поле — ровно 14 цифр и разбирается как дата UTC; иначе строка
    пропускается с `logger.warning`; непустой ответ без валидных строк → `archive_error`;
  - 403 с признаком исключения (`AdministrativeAccessControlException` / `Blocked Site`) в теле →
    «нет снимков» + `logger.info` с пометкой «исключён»;
  - 429 → перегрузка (R5); прочие 4xx/5xx, `httpx.RequestError`, ошибка декодирования → `archive_error`.
- **Rationale**: соответствует FR-010, FR-011, FR-024 и крайним случаям спецификации; конкретные
  типы исключений — требование принципа IV.
- **Alternatives considered**: считать 403 ошибкой — интерфейс показал бы «Не удалось получить
  историю» для домена, который просто скрыт.

## R3. Нормализация и проверка домена

- **Decision**: `strip()` → снять одну завершающую точку → `lower()` → отказ, если есть пробелы,
  `/`, `:`, `@`, `?`, `#` → `ascii = name.encode("idna").decode("ascii")` (встроенный кодек IDNA,
  уже используется в `services.py` для обратного преобразования) → каждая метка 1–63 символа
  `[a-z0-9-]`, не начинается и не заканчивается дефисом → общая длина ≤ 253 → ровно две метки
  (только домены второго уровня; `www.example.ru`, `shop.msk.ru` → `invalid_domain`) → зона `ru`,
  `su` или `xn--p1ai` → отображаемая форма `ascii.encode("ascii").decode("idna")`. Ключ кэша и поле
  `domain` — отображаемая форма; в архив уходит `ascii`. Любая `UnicodeError` → `invalid_domain`.
- **Rationale**: один путь для кириллицы и punycode даёт один ключ кэша (FR-012) и кириллицу
  в ответе (FR-004); проверка до постановки в очередь гарантирует «не обращаться к архиву» (FR-003).
- **Alternatives considered**: библиотека `idna` (IDNA 2008) — новая зависимость ради кириллицы,
  которую встроенный кодек обрабатывает корректно; регулярное выражение по сырой строке — не ловит
  punycode-формы и смешанный регистр кириллицы.

## R4. Модель конкурентности: асинхронный работник очереди

- **Decision**: класс `WaybackService` с `collections.deque` задач, словарём «домен → задача»
  (объединение, FR-018) и одним `asyncio.Task`-работником, который запускается лениво при первой
  постановке задачи в текущем цикле событий (правила привязки к циклу и сброса — R10). У задачи —
  `asyncio.Future` с результатом.
  Эндпоинт — `async def`; ожидание — `asyncio.wait_for(asyncio.shield(job.future), остаток_срока)`;
  `shield` не даёт таймауту клиента отменить задачу (фоновая доработка, FR-019). Обращение к архиву
  — `httpx.AsyncClient(timeout=archive_timeout)`, обёрнутое в `asyncio.wait_for(..., archive_timeout)`
  для общего таймаута: таймауты `httpx` — на отдельные операции, а не на весь ответ, и без явного
  значения `httpx` оборвал бы чтение через свои 5 с по умолчанию, раньше 10 с из FR-021. Загрузчик
  создаётся фабрикой `make_cdx_fetcher(timeout, transport=None)`; `transport` нужен тестам
  (`httpx.MockTransport`, без сети).
- **Rationale**: один работник = «не более одного обращения одновременно» (FR-017) без блокировок;
  ожидающие клиенты не занимают потоки пула; таймауты и отмена тестируются детерминированно.
- **Alternatives considered**: `threading` + `Condition` (см. Complexity Tracking в плане);
  `asyncio.Queue` — нет вставки в начало (возврат задачи после «429», FR-022) и удаления/поиска
  по домену; Celery/Redis — нарушение принципа I.
- **Следствие**: исключения в `Future` без ожидающих помечаются прочитанными через
  `add_done_callback`, чтобы не было предупреждений «exception was never retrieved».

## R5. Интервал, пауза после «429» и оценка `retry_after`

- **Decision**:
  - работник перед каждым обращением ждёт `max(last_start + interval, pause_until) - now`;
  - «429» с `Retry-After` в секундах: пауза = это значение, обрезанное константами
    `ARCHIVE_RETRY_AFTER_MIN = 1` и `ARCHIVE_RETRY_AFTER_MAX = 600` (не зависят от настройки
    `pause_max`); удвоение **не применяется** — заголовок архива главнее;
  - «429» без `Retry-After` (или в формате HTTP-даты, который не разбирается): если предыдущий
    ответ архива тоже был «429» — `min(last_pause × 2, pause_max)`, иначе `pause_default` (60 с);
  - `last_pause` запоминается после каждой паузы (в том числе заданной архивом) и обнуляется
    первым успешным обращением; ожидающим задачи отдаётся `ArchiveOverloaded`, задача получает
    новый `Future` и встаёт в начало очереди, если ещё не возвращалась, иначе снимается;
  - оценка ожидания для задачи на позиции `p` (0 — следующая): `остаток_текущего_обращения +
    max(0, pause_until - now) + p × interval + interval`, где остаток текущего — до конца его
    10-секундного таймаута; `retry_after = max(1, ceil(оценка))`;
  - при постановке: если оценка > оставшегося срока — `202` сразу (FR-019), иначе ждать до срока;
  - очередь полна → `503` с `Retry-After = max(1, ceil(interval))`; пауза → `503` с
    `Retry-After = ceil(остаток паузы)`.
- **Rationale**: оценка консервативна (по таймауту, а не по средней длительности) — клиент не придёт
  раньше времени без пользы; все числа — из спецификации и контракта.
- **Alternatives considered**: скользящая средняя длительности обращений — точнее, но
  недетерминирована в тестах; экспоненциальная пауза без предела — может «заморозить» фичу на часы.

## R6. Кэш: память + JSON-файл

- **Decision**: словарь `домен → {history, checked_at}`; свежесть `now - checked_at < 7 дней`
  (часы `time.time`, инъекция в тестах); при чтении из файла устаревшие записи отбрасываются;
  переполнение (> 10 000) — удаление записей с минимальным `checked_at`; запись файла после каждого
  нового результата в `asyncio.to_thread`, атомарно (`tmp` + `os.replace`); ошибки чтения/записи
  (`OSError`, `json.JSONDecodeError`, `ValueError` валидации) → `logger.warning`, работа продолжается
  в памяти. Путь — `WAYBACK_CACHE_PATH`, по умолчанию `<проект>/.cache/wayback_cache.json`
  (покрыт правилом `.cache` в `.gitignore` репозитория).
- **Rationale**: 7-дневный TTL бессмыслен без сохранения между перезапусками (FR-015); частота записи
  ограничена 1/с самой очередью; файл ~1–2 МБ на 10 000 записей; SQLite избыточен для словаря.
- **Alternatives considered**: только память (как `_CACHE` в `services.py`) — теряется при каждом
  перезапуске dev-сервера; `shelve`/SQLite — лишняя сложность и бинарный формат, неудобный для отладки.

## R7. Перевод ошибок в HTTP-ответы

- **Decision**: иерархия `WaybackError(Exception)` с атрибутами `code`, `status`, `detail`,
  `retry_after: int | None`: `InvalidDomain` (400), `ArchiveOverloaded` (503), `ArchiveTimeout` (504),
  `ArchiveUnavailable` (502, `archive_error`); результат «в очереди» — тоже исключение
  `HistoryPending` (не наследник `WaybackError`, статус 202). `api.py` ловит их и возвращает
  `JSONResponse(status_code, content, headers={"Retry-After": str(n)})`. Непредвиденные исключения
  внутри обработки ответа архива перехватываются в работнике и превращаются в `ArchiveUnavailable`
  с `logger.exception` (FR-026). Параметр `domain: str = ""` — без 422 FastAPI, пустое значение
  даёт `invalid_domain`.
- **Rationale**: контракт требует тела `{"code", "detail"}` на верхнем уровне; `HTTPException(detail=
  dict)` дал бы вложенный `{"detail": {...}}`. Исключения сохраняют чистую сигнатуру сервиса
  `-> WaybackHistory`.
- **Alternatives considered**: возвращать объединённый тип `WaybackHistory | Pending | Error` —
  каждому вызывающему пришлось бы ветвиться; глобальный `exception_handler` — неявен для учебного
  проекта, локальный `try/except` в эндпоинте читается проще.

## R8. Тестирование без сети и без реального времени

- **Decision**:
  - `WaybackService(settings, fetcher, clock, cache_path)` — зависимости через конструктор;
    `fetcher` — асинхронная функция «домен, limit → (status, headers, text)», в тестах — фейк
    с заданными ответами, задержками и счётчиком вызовов;
  - очередь и паузы тестируются с малыми настройками (`interval=0.01`, `deadline=0.2`,
    `archive_timeout=0.1`) в `unittest.IsolatedAsyncioTestCase`; TTL — через подменяемые часы;
  - кэш-файл — во временном каталоге (`tempfile.TemporaryDirectory`);
  - эндпоинт — `TestClient(app)` с подменой `api.get_wayback_history` через `unittest.mock.patch`
    (`AsyncMock`), проверяются статусы, тела и `Retry-After` по таблице контракта;
  - один сквозной тест эндпоинта с настоящим `WaybackService` и фейковым загрузчиком, подставленным
    через `reset_service(...)`: два последовательных запроса через `TestClient` без контекстного
    менеджера оба завершаются, второй берётся из кэша — регрессия на смену цикла (R10);
  - `setUp`/`tearDown` каждого тестового класса, затрагивающего модульный сервис, вызывают
    `reset_service()`; тесты сервиса создают свой экземпляр на каждый тест;
  - разборщик CDX тестируется на образцах из `tests/fixtures/wayback/` (R1).
- **Rationale**: принцип II (без сети, `unittest`); логика эндпоинта проверяется отдельно от цикла
  событий сервиса, а совместимость с несколькими циклами — одним целевым тестом.
- **Alternatives considered**: `respx`/`pytest-httpx` — новые зависимости и другой фреймворк тестов;
  реальные `sleep` по 1 с — тесты на минуты.

## R9. Журналирование

- **Decision**: `logger = logging.getLogger(__name__)`, как в `services.py`. `info` — каждое
  обращение к архиву (домен, итог, длительность в мс, число строк), `warning` — «429» с длительностью
  паузы, битые строки, ошибки файла кэша, `error` — таймаут/сеть/статус, `exception` — непредвиденные.
  Адреса и тексты исключений — только в журнал, не в ответ (FR-025, FR-027).
- **Rationale**: единый стиль с проектом; требование принципа IV «ошибка MUST логироваться».

## R10. Привязка к циклу событий и сброс состояния между тестами

- **Decision**:
  - при импорте `wayback.py` и `api.py` не создаётся ни одного `asyncio`-объекта (`Queue`, `Lock`,
    `Event`, `Future`, `Task`) и ни одного `httpx.AsyncClient`; модульный уровень хранит только
    `_service: WaybackService | None = None`;
  - `get_service()` создаёт сервис лениво; конструктор `WaybackService` тоже не трогает `asyncio` —
    в нём только настройки, зависимости, кэш (обычный словарь) и `deque`;
  - всё, что привязано к циклу (событие «есть работа», задача-работник, `Future` задач), создаётся
    методом `_ensure_runtime()` при первом `await get_history(...)` внутри работающего цикла;
    сервис запоминает `asyncio.get_running_loop()`;
  - если `get_history` вызван в другом цикле, чем запомненный (новый цикл `TestClient`, перезапуск
    приложения), `_ensure_runtime()` сбрасывает состояние выполнения: отменяет старого работника,
    очищает `deque`, словарь задач, паузу и время последнего обращения, пишет `logger.warning`
    и создаёт объекты заново в текущем цикле; кэш (данные, не `asyncio`) сохраняется;
  - `httpx.AsyncClient` создаётся на каждое обращение внутри загрузчика (`async with`); при частоте
    ≤ 1/с это дёшево и не привязывает клиента к циклу;
  - `Lock` не нужен: работник один, а участки между `await` в одном цикле атомарны;
  - в FastAPI — обработчик `shutdown` (рядом с существующим `mcp_client.close()`) вызывает
    `await wayback.shutdown_service()`: отменяет работника и дожидается его; при следующем старте
    всё создаётся лениво заново;
  - для тестов — `wayback.reset_service(service: WaybackService | None = None)`: отменяет работника
    текущего сервиса (если цикл ещё жив) и подставляет переданный сервис или `None`; реэкспорт
    в `services.py`. Тесты эндпоинта вызывают его в `setUp`/`tearDown`; тесты сервиса создают
    собственный `WaybackService` на тест в `IsolatedAsyncioTestCase` и не трогают модульный.
- **Rationale**: `TestClient` без контекстного менеджера выполняет запросы через портал `anyio`,
  который может поднимать новый цикл на каждый запрос или тест, а `IsolatedAsyncioTestCase` — новый
  цикл на каждый тест. Объект `asyncio`, созданный в одном цикле и использованный в другом, даёт
  `RuntimeError: ... attached to a different loop` или «вечное» ожидание `Future`, который никто не
  завершит. Ленивое создание и сброс при смене цикла делают сервис корректным в обоих случаях,
  а в рабочем режиме (`uvicorn`, один цикл) сброс никогда не срабатывает.
- **Alternatives considered**: создавать работника в `startup`/`lifespan` — проще, но тесты без
  `with TestClient(app)` его не запускают, а с ним — запускают для каждого клиента, и всё равно нужен
  сброс; переводить проект на `lifespan` вместо `@app.on_event` — затрагивает `mcp_client`,
  вне scope фичи; держать модульный сервис и требовать `with TestClient(app)` во всех тестах —
  хрупко: один забытый `with` даёт зависший тест.
- **Risk**: см. «Риски» в [plan.md](plan.md) — R-1 (смена цикла), R-2 (утечка состояния между тестами).
