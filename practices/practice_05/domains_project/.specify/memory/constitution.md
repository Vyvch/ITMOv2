# Конституция проекта «Освобождающиеся домены»

## Core Principles

### I. Простой стек: Python 3.14 + FastAPI, один HTML без сборки

- Бэкенд MUST быть написан на Python 3.14; веб-слой — FastAPI (`api.py`), CLI — `main.py`/`cli.py`.
- Фронтенд MUST состоять из одного файла `templates/index.html` с инлайн-CSS и инлайн-JS.
  Сборщики, транспиляторы, npm-зависимости и фронтенд-фреймворки запрещены.
- Новые Python-зависимости MUST добавляться в `requirements.txt` и иметь обоснование в плане фичи.
- Код MUST следовать PEP 8 и иметь аннотации типов у публичных функций.

Обоснование: учебный проект должен запускаться одной командой без инструментов сборки,
а весь UI — читаться и ревьюиться как один файл.

### II. Сначала тесты (НЕ ОБСУЖДАЕТСЯ)

- Каждое изменение поведения MUST начинаться с теста в `tests/`, который падает до реализации
  (Red → Green → Refactor).
- Тесты MUST использовать стандартный `unittest`; образец стиля — `tests/test_main.py`.
- Тесты MUST NOT ходить в сеть: внешние сервисы (nic.ru, WHOIS, DeepSeek, Wayback) подменяются
  моками.
- Работа считается готовой, только когда `python scripts/check.py` завершается с кодом 0.

Обоснование: парсинг внешних форматов и LLM-ответов хрупок; тест до кода фиксирует ожидаемое
поведение и защищает от регрессий.

### III. Неприкосновенность контракта и runner

- `docs/requirements.md` — контракт проекта. Его MUST NOT менять без явного поручения пользователя.
- `scripts/check.py` (runner проверки) MUST NOT менять без явного поручения пользователя.
- Спецификации и планы фич MUST ссылаться на соответствующий раздел контракта; при расхождении
  спецификации с контрактом приоритет у контракта.

Обоснование: контракт и runner — внешняя точка отсчёта для оценки работы; их правка «под код»
обесценивает проверку.

### IV. Внешние сервисы только через сервер

- Все обращения к внешним сервисам (auction.nic.ru, WHOIS через собственный MCP `mcp_whois.py`,
  DeepSeek, Wayback Machine) MUST выполняться на сервере (`services.py`, `mcp_client.py`).
  Клиент (`index.html`) обращается только к собственным эндпоинтам `/api/*`.
- Каждый вызов внешнего сервиса MUST иметь таймаут и обработку ошибок с конкретными типами
  исключений (сетевые, HTTP-статус, разбор формата); ошибка MUST логироваться и превращаться
  в понятный ответ (HTTP-статус с `detail` или явный fallback), а не в 500 со стектрейсом.
- Результаты дорогих или лимитированных вызовов (LLM, WHOIS, Wayback) MUST кэшироваться
  на сервере с заданным TTL.
- Секреты (например, `DEEPSEEK_API_KEY`) MUST читаться из переменных окружения и MUST NOT
  попадать в код, ответы API или HTML.

Обоснование: сервер контролирует ключи, лимиты, кэш и формат ошибок; клиент не зависит
от CORS и доступности сторонних API.

### V. Безопасный вывод в DOM

- Любые данные, пришедшие извне (имена доменов, ответы WHOIS, текст LLM, данные Wayback,
  сообщения об ошибках, пользовательский ввод), MUST вставляться в DOM через `textContent`
  или создание элементов (`createElement`), а не через `innerHTML`/шаблонные строки с HTML.
- `innerHTML` допустим только для очистки контейнера (`el.innerHTML = ''`) или статической
  разметки без интерполяции данных.
- Параметры запросов к `/api/*` MUST кодироваться через `encodeURIComponent`.

Обоснование: ответы WHOIS и LLM не контролируются нами; вставка через `innerHTML` открывает XSS.

## Технические ограничения

- Зоны: `.ru`, `.su`, `.рф`; домены `.рф` хранятся и ищутся в кириллической форме.
- Два интерфейса — CLI и веб — MUST использовать общую логику из `services.py`.
- Пользовательские регулярные выражения MUST выполняться через RE2 (`google-re2`) с ограничением
  длины, чтобы исключить ReDoS.
- Вся документация проекта (спецификации, планы, задачи, конституция, комментарии к PR)
  MUST вестись на русском языке. Идентификаторы в коде — на английском.

## Процесс разработки

- Фичи проходят цикл Spec Kit: `/speckit-specify` → `/speckit-plan` → `/speckit-tasks` →
  `/speckit-implement`; раздел «Constitution Check» в плане MUST проверять принципы I–V.
- Порядок задач в `tasks.md`: тесты раньше реализации (принцип II).
- Перед завершением фичи: `python scripts/check.py` проходит, затем код-ревью (скилл `code-review`)
  с проверкой принципов IV и V.
- Подключённые скиллы из `AGENTS.md` (fastapi, python-project-structure, python-code-style,
  python-error-handling, frontend-design, tdd, code-review) применяются к соответствующим задачам.

## Governance

- Конституция имеет приоритет над остальными практиками проекта, кроме контракта
  `docs/requirements.md`, который она не переопределяет.
- Изменение конституции — только через `/speckit-constitution` с обновлением версии и даты
  и описанием изменений в Sync Impact Report.
- Версионирование: MAJOR — удаление или переопределение принципа; MINOR — новый принцип или
  раздел, существенное расширение; PATCH — уточнения формулировок.
- Каждый план и ревью MUST проверять соответствие принципам; отступление допускается только
  с письменным обоснованием в разделе «Complexity Tracking» плана.
- Оперативные правила для агентов — в `AGENTS.md`.
