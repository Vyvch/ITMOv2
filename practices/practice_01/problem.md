# Проблема и метрики

Файл ведёт OpenCode. Обсудите с агентом содержание и проверьте предложенный diff. Все дополнения и исправления поручайте агенту в чате.

## Проблема

- Пользователь: ревьюер PR — один из 6 бэкенд-разработчиков команды, который проверяет чужие pull request в GitHub.
- Ситуация: каждый PR проходит ручное ревью; ревьюер тратит время на поиск типовых проблем (валидация входа, обработка ошибок, отсутствие тестов) до того, как перейти к сути изменения.
- Что происходит сейчас: первое ревью PR ждёт в среднем 1 рабочий день; рутинные замечания вызывают повторные итерации «правка → повторное ревью», а часть мелких ошибок доходит до main.
- Почему это мешает пользователю или бизнесу: время сеньоров уходит на рутину вместо архитектурных замечаний; автор PR простаивает в ожидании; цикл поставки фичи удлиняется.
- Что не входит в задачу: автоматический approve или merge, автоматическое исправление кода, замена ревьюера-человека, ревью более одного PR за запуск.

## Метрики

Обсудите с OpenCode показатели, по которым можно проверить решение проблемы. Агент записывает согласованный способ замера и ожидаемое изменение для каждого показателя.

| Метрика | Текущее значение или способ замера | Целевое изменение | Когда измеряем | Источник данных |
|---|---:|---:|---|---|
| Время до первого содержательного ревью PR | ~1 рабочий день (медиана по PR за месяц) | ≤ 2 часа (комментарий помощника приходит сразу после открытия PR) | Через 4 недели после внедрения | GitHub API: время между открытием PR и первым комментарием |
| Число итераций ревью на PR (циклов «замечание → правка») | Медиана 2–3 (по истории PR за месяц) | Медиана ≤ 2 | Через 4 недели | GitHub API: количество раундов review на PR |
| Доля PR с рутинными замечаниями от человека (валидация, обработка ошибок, тесты) | Замер вручную по выборке 30 PR | Снижение на 50% (рутину находит помощник до человека) | Через 4 недели | Разметка комментариев ревью по категориям |
| Полезность комментариев помощника | — (новый показатель) | ≥ 70% комментариев отмечены ревьюером как полезные | Еженедельно | Реакции 👍/👎 на комментарии помощника в PR |

## Почему изменение метрики подтвердит решение проблемы

Проблема — медленное первое ревью и трата времени людей на рутину. Если комментарий помощника приходит за минуты (метрика 1), рутинные проблемы находятся до человека (метрика 3), а число итераций падает (метрика 2), значит ревьюер занимается сутью изменения, а автор быстрее получает обратную связь. Метрика 4 контролирует качество: быстрые, но бесполезные комментарии не считаются решением.

## Как использовали AI

- Для чего: сформулировать проблему и измеримые метрики по согласованной легенде учебного кейса.
- Тип промпта: диалог в режиме Build (вопросы агента → подтверждение студента).
- Строка в [`prompts.md`](prompts.md): P1-01 — слабые места baseline-запуска показали, какие сведения о процессе и границах задачи нужно зафиксировать.
- Что проверил студент и какие исправления поручил агенту: студент подтвердил легенду процесса (ожидание ~1 день, повторные итерации из-за рутины) и границы задачи без правок.
