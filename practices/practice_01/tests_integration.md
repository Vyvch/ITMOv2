> **Краткое содержание (Executive Summary):** 
> Данный документ описывает стратегию интеграционного тестирования AI-помощника. Он включает обоснование выбора инструментов (мокинг на уровне HTTP), 5 критических тест-кейсов для проверки устойчивости связи с GitHub и VseLLM (таймауты, лимиты, безопасность), а также строгие инженерные критерии готовности (DoD).

## Выбор подхода к мокингу

Для интеграционного тестирования выбран подход **Мокинг на уровне HTTP-клиента (`pytest-httpx` / `respx`)**.
* **Почему не Dependency Injection (`app.dependency_overrides`):** Подмена классов внутри FastAPI не позволяет проверить правильность формирования HTTP-заголовков и сериализацию тела запроса перед отправкой (что критично для работы с GitHub API).
* **Почему не локальный мок-сервер (Wiremock/Docker):** Запуск полноценного сервера замедлит CI/CD пайплайн и усложнит локальный запуск тестов для нашей небольшой команды из 6 человек.
* **Итог:** `pytest-httpx` даёт оптимальный баланс: мы проверяем реальный сетевой код сервиса, но без сетевых задержек и оверхеда на инфраструктуру.

Ниже описаны конкретные сценарии интеграционных проверок с использованием выбранного инструментария.

### Сценарий 1: Таймаут от VseLLM
* **Связь компонентов:** FastAPI ➔ VseLLM API
* **Цель:** Убедиться, что сервис не зависает при долгом ожидании ответа от нейросети.
* **Инструмент:** `pytest`, `pytest-httpx`.
* **Шаги:**
  1. В фикстуре `httpx_mock` настроить роут `POST https://api.vsellm.ru/...` на выброс исключения `httpx.TimeoutException`.
  2. Вызвать обработчик вебхука `client.post("/webhook", json=payload)`.
* **Ожидаемый результат:** Сервис быстро отвечает `202 Accepted`, в логах пишется `error: VseLLM Timeout`.

### Сценарий 2: Ошибка 503 от VseLLM
* **Связь компонентов:** FastAPI ➔ VseLLM API
* **Цель:** Убедиться, что сервис перехватывает сбой сервиса генерации.
* **Инструмент:** `pytest`, `pytest-httpx`.
* **Шаги:**
  1. В фикстуре `httpx_mock` задать роут `POST https://api.vsellm.ru/...` с ответом `status_code=503`.
  2. Вызвать обработчик вебхука `client.post("/webhook", json=payload)`.
* **Ожидаемый результат:** Сервис отвечает `202 Accepted`, в логах пишется `error: VseLLM 503 Service Unavailable`.

### Сценарий 3: Обработка 500 ошибки от GitHub API
* **Связь компонентов:** FastAPI ➔ GitHub API
* **Цель:** Убедиться, что сервис корректно обрабатывает сбой API.
* **Инструмент:** `pytest`, `pytest-httpx`.
* **Шаги:**
  1. В фикстуре `httpx_mock` задать роут `POST https://api.github.com/...` с ответом `status_code=500`.
  2. Вызвать обработчик вебхука `client.post("/webhook", json=payload)`.
* **Ожидаемый результат:** Сервис отвечает `202 Accepted`, в логах пишется `error: GitHub API 500`.

### Сценарий 4: Невалидная подпись вебхука (HMAC)
* **Связь компонентов:** GitHub ➔ FastAPI
* **Цель:** Убедиться, что сервис отклоняет поддельные запросы с неверным заголовком `X-Hub-Signature-256`.
* **Инструмент:** `pytest`, `FastAPI TestClient`.
* **Шаги:**
  1. Вызвать `client.post("/webhook", json=payload, headers={"X-Hub-Signature-256": "sha256=invalid_hash"})`.
* **Ожидаемый результат:** Сервис немедленно отвечает `401 Unauthorized` (или `403 Forbidden`), вызовы к VseLLM не производятся, в лог пишется `Security: Invalid webhook signature`.

### Сценарий 5: Превышение лимитов GitHub API (Rate Limit)
* **Связь компонентов:** FastAPI ➔ GitHub API
* **Цель:** Убедиться, что сервис корректно обрабатывает блокировку по лимитам запросов, считывая заголовки GitHub.
* **Инструмент:** `pytest`, `pytest-httpx`.
* **Шаги:**
  1. В фикстуре `httpx_mock` задать роут `POST https://api.github.com/.../comments` с ответом `status_code=403`.
  2. Добавить в ответ заголовок `x-ratelimit-reset: "1710000000"`.
  3. Вызвать `client.post("/webhook", json=payload)`.
* **Ожидаемый результат:** Сервис отвечает `202 Accepted`, в лог пишется `warning: GitHub API rate limit exceeded. Reset at 1710000000`.

## Критерии готовности (Definition of Done)

* **Полная сетевая изоляция:** Интеграционные тесты не должны выполнять реальных HTTP-запросов к внешним сервисам (GitHub API, VseLLM) при запуске в CI/CD; все внешние вызовы обязаны быть замоканы.
* **Изоляция фикстур:** Каждый тест должен запускаться в чистом окружении; состояние моков должно сбрасываться после каждого тест-кейса.
* **Валидация сайд-эффектов:** Тест считается успешным только если помимо HTTP-ответа `202 Accepted` проверяется запись корректного сообщения об ошибке в лог.
* **Лимиты времени:** Интеграционный тест не должен зависать; искусственные задержки (таймауты) проверяются через мок-исключения, а не реальным `sleep`.
